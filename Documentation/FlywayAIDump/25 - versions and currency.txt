## 3. How the versions fit together

- Flyway Desktop and the Flyway engine version independently. Desktop is on its own 9.x line, and each Desktop release note names the engine build it bundles. Never infer one from the other.
- The engine inside Flyway Desktop is a release-candidate build (for example `13.10.1-rc2997`), so it can differ from the CLI on a workstation or runner. Never report a bundled release-candidate build as a released engine version.
- Three places run the engine on your team: Desktop on workstations, the CLI on workstations, and the CLI on GitHub Actions runners. Pin the runner's engine version with the `version` input of the `red-gate/setup-flyway` action, and move workstation CLIs and the runner together in one pull request.
- Keep the job that saves snapshots and the job that checks drift on the same engine version.
- The CLI and Docker image bundle their own Java runtime. A project that embeds Flyway (the Java API, Maven or Gradle) needs JDK 17 or later on engine 13; Redgate's API (Java) page has said Java 21 is required from engine 14. Not re-read on 19 October 2026, so check that page if you embed Flyway.
- SQL Compare, SQL Data Compare and SQL Prompt have their own release notes and version lines (file 19).

## 5. Code review rules and SQLFluff

The Redgate rules library runs from RG01 to RG23, and RG23 is the ceiling. Don't invent an RG24. Flyway bundles SQLFluff; don't quote its version, and ask the person to read their own `flyway check -code` output. The rules library page notes an operating-system floor for the bundled rules on Linux, so use a current runner image or your own SQLFluff install.

## 6. Builds to avoid

Never install or recommend these Flyway Desktop builds, which the Desktop 9 release notes mark as pulled: 9.7.2, 9.2.3, 9.2.4 and 9.2.5. No later build was marked as pulled on 19 October 2026. If someone is on a pulled build, tell them to upgrade to the newest listed release.

## 7. Deprecations

From the engine release notes:
- `checkDriftOnMigrate` is deprecated from engine 13.10.0 and logs a warning when used. Use `check -drift`. Nobody should enable it.
- `flywayServicePublish.publishReport` is deprecated from engine 13.10.0 and logs a warning when used. Use `publishResult` if you turn Insights on (file 18).
- Code review severity and policy settings from engine 12 and earlier are removed. Take current settings from the code review rules page, not from older examples.

## 8. Version floors and upgrade watch-outs

Newest first. When someone upgrades, read only the items between their version and the target.

- Engine 13.10.1: Flyway prints the name of the environment it's working on and warns when two environment names differ only by case. With one `ci/<environment>.toml` per environment, check the printed name in the first pipeline run after upgrading.
- Desktop, 14 October 2026 (unnumbered entry): object level history out of preview. Nothing to configure.
- Engine 13.10.0: plugin parameters such as `check.buildEnvironment` and `undoSqlMigrationPrefix` can be set per environment under `[environments.<name>.flyway]`. Prove it on your engine before a pipeline relies on it. This is also the floor for publishing to Flyway Insights from chosen environments only (`publishResult = false` under `[flyway]`, `publishResult = true` under `[environments.<name>.flyway]`): use an engine later than 13.10.0, and test on your exact version that a non-production run publishes nothing (file 18).
- Desktop 9.10.3: Desktop deletes log files older than a month when it starts. If you keep them as audit evidence, change Settings > Log retention.
- Desktop 9.10.2: publishing to Flyway Insights can be switched on from project settings. Read the data policy in file 18 first.
- Engine 13.9.0: Flyway no longer inherits the operating system proxy by default (`FLYWAY_USE_SYSTEM_PROXIES` defaults to false). Machines behind a proxy lose licensing and update calls until you set it to true or set the proxy in `JAVA_ARGS`. On Linux runners and the Docker image, use `JAVA_ARGS`.
- Engine 13.9.0: Flyway Report has a new implementation, on by default. `FLYWAY_NEW_REPORTS=false` restores the legacy report for anything that parses it.
- Engine 13.9.0: `init` no longer writes the root `redgateCompare.filterFile` setting for SQL Server projects.
- Engine 13.8.0: connections report the application name `Redgate_Flyway` (it was "Flyway by Redgate"). Update any Redgate Monitor filter, audit rule or logon trigger keyed on the old name (file 19). Drift results are published to Insights for any drift check when `publishResult` is on.
- Desktop 9.10.0: deploying from Flyway Desktop saves a snapshot by default. The CLI is unchanged: `deploy.saveSnapshot` defaults to false, so a hand-written pipeline sets it or runs `flyway snapshot` (file 14).
- Engine 13.7.0: generated migration filename timestamps use UTC, not local time. With parallel branches across time zones, check ordering with `info` before merging (file 09). The same release stopped drift results being published to Insights when `publishResult` is false.
- Engine 13.6.0: after upgrading a workstation across 13.6.0, run `flyway auth` once more. Runners using `FLYWAY_EMAIL` and `FLYWAY_TOKEN` are unaffected.
- Engine 13.0.0: the first release that carries the Flyway MCP server.

|---|---|

| SQL Prompt | The About entry in SQL Prompt's menu in SSMS or Visual Studio |

## 12. Instructions for the AI assistant using this file

- This is the only file you may quote a current version or preview status from. If another file seems to state one, prefer this file and tell the person about the conflict.
- Always give the date with a version, for example "engine 13.10.2, checked 19 October 2026". For Flyway Desktop, say 9.10.6 is the newest numbered release as of that date, and that an unnumbered 14 October entry sits above it.
- If today is more than about a month after 19 October 2026, say the version may have moved and give the release notes link from section 11 instead of asserting it.
- Never describe a Desktop-bundled release-candidate build as an engine release, never cite a version from example output on a docs page, and never suggest a pulled build or an unpinned runner version.
- When someone asks about upgrading, ask for their current version first, then list only the section 8 items between it and the target.
- Never quote the bundled SQLFluff version. Point people at their own `flyway check -code` output.
- Label preview capabilities "(preview)" every time.
- Answer in the language the person writes in. Keep versions, commands and keys in English.
