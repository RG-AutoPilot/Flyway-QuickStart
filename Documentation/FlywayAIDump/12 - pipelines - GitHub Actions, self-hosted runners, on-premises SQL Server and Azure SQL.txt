## 1. Repository layout and secrets

> Not from Redgate docs — starting point, validate in your environment.

```text
.github/workflows/
  flyway-pr.yml              pull request validation
  flyway-release.yml         package once, test -> uat, production on demand
  flyway-drift-nightly.yml   scheduled drift check
ci/
  build.toml  test.toml  uat.toml  production.toml
migrations/  callbacks/  flyway.toml  CODEOWNERS
```

- Each `ci/<env>.toml` (file 10) reads `${env.FLYWAY_<ENV>_URL}`, `${env.FLYWAY_<ENV>_USER}` and `${env.FLYWAY_<ENV>_PASSWORD}`. Each step loads only its own file, and the job maps exactly those variables: the read-only check account in check jobs, the deploy account in deploy jobs.
- Prove with `flyway info -X` in your proof of concept that `-configFiles` adds to the automatic `flyway.toml` and that `${env.X}` resolves. The documented fallback is variables named `environments_<env>_<setting>` (file 10).
- `CODEOWNERS` covers `.github/workflows/`, `ci/` and `migrations/`.

| Where | Secrets |
|---|---|
| Repository | `FLYWAY_EMAIL`, `FLYWAY_TOKEN`; `FLYWAY_BUILD_URL`, `_USER`, `_PASSWORD`; `FLYWAY_TEST_URL`, `FLYWAY_TEST_CHECK_USER`, `FLYWAY_TEST_CHECK_PASSWORD` |
| Environments `test`, `uat`, `production` | `FLYWAY_URL`, `FLYWAY_DEPLOY_USER`, `FLYWAY_DEPLOY_PASSWORD` |
| Environment `production-read-only` | `FLYWAY_URL`, `FLYWAY_CHECK_USER`, `FLYWAY_CHECK_PASSWORD` |

Repository variable `FLYWAY_VERSION` pins the engine (file 25).

## 2. Fast start to a first green pull request check

1. Register one self-hosted runner labeled `<runner-label>` that can reach `test` and the build server (section 8).
2. Add the repository secrets and `FLYWAY_VERSION`.
3. Commit `ci/build.toml` and `ci/test.toml` (file 10).
4. From a workflow on that runner, run `flyway testConnection -configFiles=ci/test.toml -environment=test`, then `flyway info` with the same arguments.
5. Add `flyway-pr.yml` (section 11) and make `validate` a required status check.

Keep real deployment disabled until `testConnection`, `info` and `check -dryrun` work from the runner.

## 3. Redgate's actions: names, inputs and what they run

- `red-gate/setup-flyway@v3` installs and licenses the command line. Required inputs: `edition: enterprise` and `i-agree-to-the-eula: true`. Also `version` (default `latest`, so always set it), `email`, `token`, `architecture`, `platform`. Examples of `@v1` with `edition` look current but aren't, and the older `red-gate/FlywayGithubAction` is deprecated.
- `red-gate/flyway-actions/<path>@v2` holds six step actions. Use one version for all of them, as Redgate's README says, pin each to a full commit SHA in production, and run engine 12.0.0 or later.

Every step action takes `target-environment` or `target-url`, plus `target-user`, `target-password`, `target-schemas`, `working-directory` and `extra-args`. A named `target-environment` becomes `-environment=<env>`, so your loaded configuration supplies whatever you leave out.

| Action | Command line it runs | Inputs that matter | Outputs |
|---|---|---|---|
| `migrations/checks` | `flyway check` with `-code`, `-drift`, `-changes`, `-dryrun`, each skippable | `build-environment` or `build-url`/`-user`/`-password`; `build-ok-to-erase`; `build-docker-i-agree-to-the-db-vendors-eula`; `skip-code-review`, `skip-drift-check`, `skip-deployment-changes-report`, `skip-deployment-script-review`; `fail-on-code-review`, `fail-on-drift` (both default `true`) | `exit-code`, `drift-detected`, `changed-object-count`, `code-violation-count`, `code-violation-codes` |
| `migrations/deploy` | `check -drift` failing on drift, then `migrate` with `-baselineOnMigrate` and `-migrate.saveSnapshot=true` | `baseline-on-migrate` (default `true`), `skip-drift-check`, `skip-snapshot`, `provision-mode`, `target-migration-version`, `cherry-pick` | `exit-code`, `drift-detected`, `migrations-applied`, `schema-version` |
| `migrations/undo` | Drift check, `undo`, snapshot | `target-migration-version`, `cherry-pick`, `skip-*` | adds `migrations-undone` |
| `migrations/generate` | `diff`, `generate`, then a Git commit and push | `source` (default `schemaModel`), `migration-types`, `migration-description`, `build-*`, `commit-migrations` (default `true`) | `script-paths`, `committed` |
| `state/prepare` | Drift check, code review, change report, `prepare` to `deployments/D__<env>_deployment.sql` | `generate-undo` (default `true`), `fail-on-drift`, `fail-on-code-review`, `skip-*` | `script-path`, `undo-script-path` |
| `state/deploy` | Drift check, `deploy` of the script, snapshot | `script-path`, `skip-drift-check`, `skip-snapshot` | `exit-code`, `drift-detected` |

Reports and drift-resolution scripts upload as artifacts, kept 7 days unless you set the retention inputs to your audit period (file 17). Chain `state/prepare` to `state/deploy` with `steps.<id>.outputs.script-path`.

## 4. Defaults that catch people out

- **`migrations/deploy` baselines by default.** A non-empty database with no history table is silently baselined. Set `baseline-on-migrate: 'false'` once a target is baselined (file 07).
- **`migrations/deploy` always fails on drift.** There's no `fail-on-drift` input. An out-of-band hotfix stops the release until it's brought into source control (file 11, section 12); `skip-drift-check` is a recorded exception.
- **`migrations/checks` provisions a Docker build database (preview)** when you name no build database. It needs Docker on the runner and, for SQL Server, `build-docker-i-agree-to-the-db-vendors-eula: 'true'` to accept Microsoft's license. Without either, the change report is skipped with a warning, not failed. Windows runners rarely have Linux Docker, so name a build database there, never a shared one: the action may clean it.
- **Code scanning upload.** On a private repository it needs GitHub's code security feature, `security-events: write` and `actions: read`; a failed upload doesn't fail the action. Violation counts aren't set while `fail-on-code-review` is `true`.
- **Artifact names collide** when one action runs twice for the same environment, or in a matrix; set unique report names.
- **`generate` pushes.** It needs `contents: write`. A push made with the default `GITHUB_TOKEN` doesn't trigger new runs, so use an app token if the generated commit must be checked.
- **Plumbing.** The actions run under `shell: bash`, install Node.js on self-hosted runners if missing (preinstall it on a locked-down network), and upload with newer artifact actions (section 6).

## 5. The workflow Flyway Desktop generates

Desktop's "Automate deployment" page writes a workflow on the same actions: `checks` and `deploy` for migrations-based projects, `state/prepare` and `state/deploy` for state-based ones.

- **Trigger and shape:** `workflow_dispatch` only (add `push` or `schedule` yourself). Each pipeline step is a job, in sequence; several targets in one step run as a matrix. Deploy all pending, up to a `target`, or a `cherryPick`.
- **"Manual review required"** splits a step into `<step>-read-only` (checks and reports) and `<step>-write` (deploy) jobs in matching GitHub environments, such as `production-read-only` and `production-write`. Desktop doesn't configure GitHub: add required reviewers to the `-write` environment and limit it to `main`. No reviewer means no gate.
- **Secrets:** `environments_<id>_user` and `environments_<id>_password` per environment, falling back to `FLYWAY_USER`/`FLYWAY_PASSWORD` and `FLYWAY_BUILD_USER`/`FLYWAY_BUILD_PASSWORD`. An ID with a hyphen or dot can't form a variable name and silently uses the fallback, so name environments with letters, digits and underscores.
- **Your adjustments:** the Git Bash step and, for integrated authentication, no user or password inputs (section 8); a self-hosted runner for private databases; `baseline-on-migrate: 'false'`.

This file calls the gated environment `production`; Desktop calls it `production-write`. Pick one convention. Treat the generated file as a seed for the shared workflows (section 14).

## 6. GitHub plans: Team, Enterprise Cloud and Enterprise Server

For private or internal repositories:

| Feature | Team | Enterprise Cloud | Enterprise Server |
|---|---|---|---|
| Environments, environment secrets, deployment branch rules | Yes | Yes | Yes |
| Required reviewers, prevent self-review, wait timer, no administrator bypass | Public repositories only | Yes | Yes |
| Branch protection, rulesets, runner groups limited to repositories | Yes | Yes | Yes |
| Runner groups limited to named workflows | No | Yes | Yes |

**GitHub Team:** no required-reviewer gate on a private repository, so Desktop's "Manual review required" workflow runs straight through. Options, strongest first: upgrade; or approve through a pull request into a protected `release` branch with required approvals and the Flyway checks as a required status, limit `production` deployments to `release`, and deploy only the validated commit SHA (file 11, section 4); or a `workflow_dispatch`-only deploy limited by repository permissions, which records no named approver.

**GitHub Enterprise Server:** `actions/upload-artifact` and `download-artifact` from v4 aren't supported, and `flyway-actions` uploads with newer ones, so expect its report uploads to fail; Redgate doesn't document Enterprise Server. Workaround: run the file 11, section 9 commands as plain steps with `-reportFilename`, and upload with the v3 artifact actions. The v3 download can't fetch another run's artifact, so promote by commit: read the tested run's commit with `gh run view <run-id> --json headSha`, check out that SHA and verify it (file 11, section 4). Sync the Redgate actions to the server or reach them through GitHub Connect.

## 7. Installing and licensing Flyway on runners

- Use `setup-flyway` with `version: ${{ vars.FLYWAY_VERSION }}` where the runner reaches Redgate's downloads. Otherwise preinstall the pinned Redgate command line (not the open-source package) or the pinned `redgate/flyway` image.
- License with `FLYWAY_EMAIL` and `FLYWAY_TOKEN` for a service account, never a license key. Run `flyway version` early: an unlicensed runner silently skips drift checks and snapshots in the actions.
- On Linux and in containers set the proxy in `JAVA_ARGS` (file 23). Never run fork pull requests on a self-hosted runner; they get no secrets anyway.

**Isolated runners: offline permit.** Store the command-line permit base64-encoded as a secret, decode it at run time and point `FLYWAY_OFFLINE_PERMIT_PATH` at the file. `setup-flyway` and `docker pull` need the internet, so preinstall. A permit lasts up to a year with no automatic refresh, and an expired one drops to Community features instead of failing, so check the banner and schedule the renewal (file 04).

> Not from Redgate docs — starting point, validate in your environment.

```yaml
      - name: Stage offline permit
        shell: bash
        env:
          PERMIT_B64: ${{ secrets.FLYWAY_OFFLINE_PERMIT }}
        run: |
          echo "$PERMIT_B64" | base64 --decode > "$RUNNER_TEMP/permit.dat"
          echo "FLYWAY_OFFLINE_PERMIT_PATH=$RUNNER_TEMP/permit.dat" >> "$GITHUB_ENV"
      - run: flyway version   # expect Enterprise in the banner
        shell: bash
```

## 8. Self-hosted runners for on-premises SQL Server

GitHub-hosted runners can't reach a private SQL Server, so those jobs run on self-hosted runners inside your network.

- **Windows: Git Bash ahead of WSL.** The actions run under `shell: bash`, and on Windows `bash` can resolve to the WSL launcher, which can't read the runner's paths. Redgate's samples prepend Git for Windows to the path as the first step of each Windows job, as the workflows below do:

> Not from Redgate docs — starting point, validate in your environment.

```yaml
      - name: Git Bash ahead of WSL bash
        if: runner.os == 'Windows'
        shell: pwsh
        run: '"C:\Program Files\Git\bin", "C:\Program Files\Git\usr\bin" | Add-Content $env:GITHUB_PATH'
```

- **Windows integrated authentication.** The runner service runs as a domain service account; the URL has `integratedSecurity=true`. Omit user and password inputs rather than passing blanks, because an empty user breaks integrated security.
- **Linux: Kerberos.** Put `integratedSecurity=true` and `authenticationScheme=JavaKerberos` in the URL, and set `kerberosConfigFile` and `sqlserver.kerberos.login.file`. Keep the keytab as a base64 secret decoded to `$RUNNER_TEMP`. Clock skew and reaching the key distribution center are the usual failures. Otherwise use SQL logins.
- **One identity per runner.** Read-only and deploy identities under integrated authentication need two runners, two service accounts and two runner groups.
- **Groups, labels, isolation.** Restrict production-capable runner groups to the repositories (on Enterprise, the workflows) that deploy, and select them with `runs-on: [self-hosted, windows, <runner-label>]`. Environment secrets on a self-hosted runner are only as private as the runner, so prefer `--ephemeral` runners.
- **Network.** Outbound HTTPS to GitHub, TCP to the SQL Server port, `encrypt=true` and certificate trust per your policy (file 23). Add `errorOverrides = ["S0001:0:I-"]` so `PRINT` output reports as information.

## 9. Azure SQL Database and Managed Instance authentication

Both services take the same options. GitHub-hosted runners suit Azure SQL Database when its firewall or a public endpoint admits them; on-premises SQL Server always needs a self-hosted runner (section 8). A Managed Instance's VNet-local endpoint needs a runner in or peered with that network, or hosted runners on Azure private networking (Enterprise Cloud). Prefer a private endpoint to opening a firewall to GitHub's shared address ranges.

| Option | Flyway configuration | Stored secret | Fits |
|---|---|---|---|
| OIDC, then an access token | `azure/login`, then `az account get-access-token --resource https://database.windows.net/` into the `accessToken` JDBC property | None | Any runner that reaches the server; tokens last 60 to 90 minutes |
| Service principal | `authentication=ActiveDirectoryServicePrincipal`, client ID as `user`, secret as `password` | Client secret | Redgate's recommended pipeline route; long runs |
| Managed identity | `authentication=ActiveDirectoryMSI` (`msiClientId` if user-assigned) | None | Self-hosted runners on Azure virtual machines |
| Azure Key Vault resolver | `password = "${azureKeyVault.<secret-name>}"` (file 10) | In the vault | Flyway uses the Azure SDK's standard credential chain, so an `azure/login` sign-in, managed identity or service principal variables are picked up. Read a test secret in the POC |
| SQL login | `user` and `password` from environment secrets | Password | Where Entra isn't set up |

`authentication=ActiveDirectoryDefault` is a Microsoft driver mode Redgate's tutorials don't cover; prove it first.

OIDC setup: an Entra app registration with a federated credential per GitHub environment (audience `api://AzureADTokenExchange`, subject `repo:<org>/<repo>:environment:<env>`, case-sensitive, copied exactly as GitHub issues it); `CREATE USER [<app-name>] FROM EXTERNAL PROVIDER;` with the file 10 rights; job permissions `id-token: write` and `contents: read`. The `ci/<env>.toml` holds only the URL (`jdbc:sqlserver://<azure-sql-server>.database.windows.net:1433;databaseName=<db-name>;encrypt=true`), and the job adds:

> Not from Redgate docs — starting point, validate in your environment.

```yaml
    permissions: { id-token: write, contents: read }
    env:
      AZURE_CORE_OUTPUT: none
    steps:
      - uses: azure/login@v3   # pin to a full commit SHA
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
          allow-no-subscriptions: true
      - name: Entra access token for Azure SQL
        shell: bash
        run: |
          TOKEN=$(az account get-access-token --resource https://database.windows.net/ --query accessToken -o tsv)
          echo "::add-mask::$TOKEN"
          echo "environments_uat_jdbcProperties_accessToken=$TOKEN" >> "$GITHUB_ENV"
```

Prove the variable's letter case on your runner OS; `-environments.<env>.jdbcProperties.accessToken=` through `extra-args` is the fallback. For Key Vault, keep `azure/login` and drop the token step.

## 10. Environments, approvals and concurrency

| Environment | Used by | Protection |
|---|---|---|
| `test`, `uat` | Deploy jobs | Deployment branch `main`; reviewers on `uat` if your policy asks |
| `production-read-only` | Production checks, nightly drift | Deployment branch `main`; read-only account secrets; no reviewers |
| `production` | Production deploy | Required reviewers; prevent self-reviews; deployment branch `main`; administrator bypass disallowed |

- Required reviewers: up to six users or teams, one approval needed. Environment secrets reach a job only after its protection rules pass. A workflow that names a missing environment creates it unprotected, so create all four first. Section 6 covers plan limits.
- Concurrency allows one running job per group. By default a newer pending job replaces an older pending one; `queue: max` keeps waiting runs, in an order GitHub doesn't guarantee, and can't be combined with `cancel-in-progress: true`. Never set `cancel-in-progress: true` on a deploy job.

## 11. Workflow 1: pull request validation

> Not from Redgate docs — starting point, validate in your environment.

```yaml
# .github/workflows/flyway-pr.yml
name: flyway-pr
on:
  pull_request:
    branches: [main]
    paths: ['migrations/**', 'callbacks/**', 'flyway.toml', 'ci/**']
permissions:
  contents: read
concurrency:
  group: flyway-build          # one shared build database
  cancel-in-progress: false
  queue: max                   # keep every waiting pull request run
jobs:
  validate:
    name: validate
    if: github.event.pull_request.head.repo.full_name == github.repository
    runs-on: [self-hosted, windows, <runner-label>]
    env:
      FLYWAY_BUILD_URL: ${{ secrets.FLYWAY_BUILD_URL }}
      FLYWAY_BUILD_USER: ${{ secrets.FLYWAY_BUILD_USER }}
      FLYWAY_BUILD_PASSWORD: ${{ secrets.FLYWAY_BUILD_PASSWORD }}
      FLYWAY_TEST_URL: ${{ secrets.FLYWAY_TEST_URL }}
      FLYWAY_TEST_USER: ${{ secrets.FLYWAY_TEST_CHECK_USER }}
      FLYWAY_TEST_PASSWORD: ${{ secrets.FLYWAY_TEST_CHECK_PASSWORD }}
    steps:
      - name: Git Bash ahead of WSL bash
        if: runner.os == 'Windows'
        shell: pwsh
        run: '"C:\Program Files\Git\bin", "C:\Program Files\Git\usr\bin" | Add-Content $env:GITHUB_PATH'
      - uses: actions/checkout@v7   # pin to a full commit SHA
        with: { fetch-depth: 0 }
      - name: Version collision and lowest new version
        shell: bash
        run: |
          git fetch origin main --quiet
          fail=0; lowest=""
          while IFS= read -r f; do
            [ -z "$f" ] && continue
            v=$(basename "$f" | sed -E 's/^V([^_]+)__.*/\1/')
            if git ls-tree -r --name-only origin/main -- migrations | grep -qE "(^|/)V${v}__"; then
              echo "::error::Version $v already exists on main ($f)"; fail=1
            fi
            if [ -z "$lowest" ] || [ "$(printf '%s\n%s\n' "$v" "$lowest" | sort -V | head -n1)" = "$v" ]; then lowest="$v"; fi
          done < <(git diff --name-only --diff-filter=A origin/main...HEAD -- migrations | grep -E '(^|/)V[^/]*__' || true)
          echo "LOWEST_NEW=$lowest" >> "$GITHUB_ENV"
          exit $fail
      - uses: red-gate/setup-flyway@v3
        with: { edition: enterprise, i-agree-to-the-eula: true, version: '${{ vars.FLYWAY_VERSION }}', email: '${{ secrets.FLYWAY_EMAIL }}', token: '${{ secrets.FLYWAY_TOKEN }}' }
      - name: Build from scratch
        shell: bash
        run: flyway clean migrate -configFiles=ci/build.toml -environment=build -cleanDisabled=false -failOnMissingLocations=true
      - name: Undo round trip
        if: env.LOWEST_NEW != ''
        shell: bash
        run: |
          flyway undo -configFiles=ci/build.toml -environment=build -target="$LOWEST_NEW"
          flyway migrate -configFiles=ci/build.toml -environment=build
      - name: Checks (code review, change report on build, dry run against test)
        id: checks
        uses: red-gate/flyway-actions/migrations/checks@v2
        with:
          target-environment: test
          build-environment: build
          build-ok-to-erase: 'true'
          skip-drift-check: 'true'   # drift is checked before each deploy and nightly
          extra-args: -configFiles=ci/test.toml,ci/build.toml
      - name: Summary
        if: always()
        shell: bash
        run: |
          echo "Code violations ${{ steps.checks.outputs.code-violation-count }} (${{ steps.checks.outputs.code-violation-codes }}), changed objects ${{ steps.checks.outputs.changed-object-count }}" >> "$GITHUB_STEP_SUMMARY"
```

In order: the collision check (file 09), a build from scratch on the disposable `build` database, the undo round trip (file 13), then the checks action: code review, the change report on `build` and the dry run against `test` with the read-only account. The `if` line skips fork pull requests.

Branch protection on `main`: require a pull request, the `validate` check and up-to-date branches; require code-owner review; block force pushes and deletion.

## 12. Workflow 2: release, promotion and production

A push to `main` packages the migrations once and deploys to `test`, then `uat`. A manual `workflow_dispatch` naming a tested run verifies it, checks production read-only, waits for approval and deploys the same package. `workflow_dispatch` runs only from the file on the default branch: use the Actions tab or `gh workflow run flyway-release.yml -f run-id=<run-id>`.

> Not from Redgate docs — starting point, validate in your environment.

```yaml
# .github/workflows/flyway-release.yml
name: flyway-release
on:
  push:
    branches: [main]
    paths: ['migrations/**', 'callbacks/**', 'flyway.toml', 'ci/**']
  workflow_dispatch:
    inputs:
      run-id:
        description: Run ID of a flyway-release push run that passed test and uat
        required: true
permissions:
  contents: read
  actions: read    # read an earlier run and download its artifact
jobs:
  package:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7   # pin to a full commit SHA
      - name: Package once
        run: |
          tar -czf flyway-package.tar.gz migrations flyway.toml ci   # add callbacks and the filter file if used
          sha256sum flyway-package.tar.gz > flyway-package.tar.gz.sha256
      - uses: actions/upload-artifact@v7
        with:
          name: flyway-package
          path: |
            flyway-package.tar.gz
            flyway-package.tar.gz.sha256
          retention-days: 90
          if-no-files-found: error

  deploy-test:
    needs: package
    runs-on: [self-hosted, windows, <runner-label>]
    environment: test
    concurrency: { group: flyway-test, cancel-in-progress: false }
    env:
      FLYWAY_TEST_URL: ${{ secrets.FLYWAY_URL }}
      FLYWAY_TEST_USER: ${{ secrets.FLYWAY_DEPLOY_USER }}
      FLYWAY_TEST_PASSWORD: ${{ secrets.FLYWAY_DEPLOY_PASSWORD }}
    steps:
      - if: runner.os == 'Windows'   # Git Bash ahead of WSL bash (section 8)
        shell: pwsh
        run: '"C:\Program Files\Git\bin", "C:\Program Files\Git\usr\bin" | Add-Content $env:GITHUB_PATH'
      - uses: actions/download-artifact@v8
        with: { name: flyway-package }
      - shell: bash
        run: sha256sum -c flyway-package.tar.gz.sha256 && tar -xzf flyway-package.tar.gz
      - uses: red-gate/setup-flyway@v3
        with: { edition: enterprise, i-agree-to-the-eula: true, version: '${{ vars.FLYWAY_VERSION }}', email: '${{ secrets.FLYWAY_EMAIL }}', token: '${{ secrets.FLYWAY_TOKEN }}' }
      - uses: red-gate/flyway-actions/migrations/deploy@v2
        with:
          target-environment: test
          baseline-on-migrate: 'false'
          extra-args: -configFiles=ci/test.toml -installedBy=${{ github.run_id }} -failOnMissingLocations=true

  # deploy-uat: copy deploy-test, replace every "test"/"TEST" with "uat"/"UAT", and set needs: deploy-test

  verify-source:
    if: github.event_name == 'workflow_dispatch' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: Source must be a green push run of this workflow on main
        shell: bash
        env:
          GH_TOKEN: ${{ github.token }}
          RUN_ID: ${{ inputs.run-id }}
        run: |
          [[ "$RUN_ID" =~ ^[0-9]+$ ]] || { echo "::error::run-id must be numeric"; exit 1; }
          gh run view "$RUN_ID" --repo "$GITHUB_REPOSITORY" --json conclusion,headBranch,event,workflowName \
            --jq '.conclusion=="success" and .headBranch=="main" and .event=="push" and .workflowName=="flyway-release"' \
            | grep -qx true || { echo "::error::Run $RUN_ID is not a tested run of this workflow"; exit 1; }

  production-checks:
    needs: verify-source
    runs-on: [self-hosted, windows, <runner-label>]
    environment: production-read-only
    concurrency: { group: flyway-production, cancel-in-progress: false }
    outputs:
      package-sha: ${{ steps.pkg.outputs.sha }}
    env:
      FLYWAY_PRODUCTION_URL: ${{ secrets.FLYWAY_URL }}
      FLYWAY_PRODUCTION_USER: ${{ secrets.FLYWAY_CHECK_USER }}
      FLYWAY_PRODUCTION_PASSWORD: ${{ secrets.FLYWAY_CHECK_PASSWORD }}
    steps:
      - if: runner.os == 'Windows'   # Git Bash ahead of WSL bash (section 8)
        shell: pwsh
        run: '"C:\Program Files\Git\bin", "C:\Program Files\Git\usr\bin" | Add-Content $env:GITHUB_PATH'
      - uses: actions/download-artifact@v8
        with: { name: flyway-package, run-id: '${{ inputs.run-id }}', github-token: '${{ github.token }}' }
      - id: pkg
        shell: bash
        run: |
          sha256sum -c flyway-package.tar.gz.sha256 && tar -xzf flyway-package.tar.gz
          echo "sha=$(cut -d' ' -f1 flyway-package.tar.gz.sha256)" >> "$GITHUB_OUTPUT"
      - uses: red-gate/setup-flyway@v3
        with: { edition: enterprise, i-agree-to-the-eula: true, version: '${{ vars.FLYWAY_VERSION }}', email: '${{ secrets.FLYWAY_EMAIL }}', token: '${{ secrets.FLYWAY_TOKEN }}' }
      - name: Production preview and drift (read-only)
        id: checks
        uses: red-gate/flyway-actions/migrations/checks@v2
        with:
          target-environment: production
          skip-code-review: 'true'                 # done in the pull request
          skip-deployment-changes-report: 'true'   # needs a build database; done in the pull request
          fail-on-drift: 'true'
          extra-args: -configFiles=ci/production.toml
      - if: always()
        shell: bash
        run: |
          echo "Run ${{ inputs.run-id }}, package ${{ steps.pkg.outputs.sha }}, drift ${{ steps.checks.outputs.drift-detected }}. Read flyway-production-pre-deployment-report before approving." >> "$GITHUB_STEP_SUMMARY"

  production-deploy:
    needs: production-checks
    runs-on: [self-hosted, windows, <runner-label>]
    environment: production        # required reviewers, prevent self-reviews, branch main
    concurrency: { group: flyway-production, cancel-in-progress: false }
    env:
      FLYWAY_PRODUCTION_URL: ${{ secrets.FLYWAY_URL }}
      FLYWAY_PRODUCTION_USER: ${{ secrets.FLYWAY_DEPLOY_USER }}
      FLYWAY_PRODUCTION_PASSWORD: ${{ secrets.FLYWAY_DEPLOY_PASSWORD }}
    steps:
      - if: runner.os == 'Windows'   # Git Bash ahead of WSL bash (section 8)
        shell: pwsh
        run: '"C:\Program Files\Git\bin", "C:\Program Files\Git\usr\bin" | Add-Content $env:GITHUB_PATH'
      - uses: actions/download-artifact@v8
        with: { name: flyway-package, run-id: '${{ inputs.run-id }}', github-token: '${{ github.token }}' }
      - name: Same package the approver saw
        shell: bash
        run: |
          sha256sum -c flyway-package.tar.gz.sha256
          [ "$(cut -d' ' -f1 flyway-package.tar.gz.sha256)" = "${{ needs.production-checks.outputs.package-sha }}" ]
          tar -xzf flyway-package.tar.gz
      - uses: red-gate/setup-flyway@v3
        with: { edition: enterprise, i-agree-to-the-eula: true, version: '${{ vars.FLYWAY_VERSION }}', email: '${{ secrets.FLYWAY_EMAIL }}', token: '${{ secrets.FLYWAY_TOKEN }}' }
      - name: Drift gate, then deploy to production
        id: deploy
        uses: red-gate/flyway-actions/migrations/deploy@v2
        with:
          target-environment: production
          baseline-on-migrate: 'false'
          extra-args: -configFiles=ci/production.toml -installedBy=${{ github.run_id }} -failOnMissingLocations=true
      - name: Post-deployment verification
        shell: bash
        run: |
          flyway info -configFiles=ci/production.toml -environment=production
          flyway validate -configFiles=ci/production.toml -environment=production
      - if: always()
        shell: bash
        run: |
          echo "Production: applied ${{ steps.deploy.outputs.migrations-applied }}, now at ${{ steps.deploy.outputs.schema-version }}" >> "$GITHUB_STEP_SUMMARY"
```

How it maps to file 11:

- **Build once, promote one tested run.** Every later job downloads the one archive and checks its checksum; `verify-source` accepts only a green `push` run on `main`, so `test` and `uat` both passed. The `github.ref` check covers the Run workflow form's branch selector. Artifacts expire (90 days at most), and Enterprise Server promotes by commit SHA (section 6).
- **The preview is what's approved.** `production-checks` publishes the dry run and drift result before approval, under the read-only account. `production-deploy` confirms the same package, then the deploy action re-checks drift, migrates and saves a snapshot.
- **Several databases (file 11, section 11):** copy the check and deploy jobs per database, chained with `needs:` in dependency order. **Hotfix:** `-outOfOrder=true` or `cherry-pick` for the approved run only (file 11, section 12). **Production undo:** a separate manual workflow with `migrations/undo` behind `production`. **Azure SQL:** add the section 9 steps to that environment's jobs. **State-based:** `state/prepare` in the read-only job, `state/deploy` of that `script-path` in the approved job.

## 13. Workflow 3: nightly drift check

> Not from Redgate docs — starting point, validate in your environment.

```yaml
# .github/workflows/flyway-drift-nightly.yml
name: flyway-drift-nightly
on:
  schedule:
    - cron: '30 2 * * *'
  workflow_dispatch:
permissions:
  contents: read
  issues: write
jobs:
  drift-production:
    runs-on: [self-hosted, windows, <runner-label>]
    environment: production-read-only
    env:
      FLYWAY_PRODUCTION_URL: ${{ secrets.FLYWAY_URL }}
      FLYWAY_PRODUCTION_USER: ${{ secrets.FLYWAY_CHECK_USER }}
      FLYWAY_PRODUCTION_PASSWORD: ${{ secrets.FLYWAY_CHECK_PASSWORD }}
    steps:
      - if: runner.os == 'Windows'   # Git Bash ahead of WSL bash (section 8)
        shell: pwsh
        run: '"C:\Program Files\Git\bin", "C:\Program Files\Git\usr\bin" | Add-Content $env:GITHUB_PATH'
      - uses: actions/checkout@v7   # pin to a full commit SHA
      - uses: red-gate/setup-flyway@v3
        with: { edition: enterprise, i-agree-to-the-eula: true, version: '${{ vars.FLYWAY_VERSION }}', email: '${{ secrets.FLYWAY_EMAIL }}', token: '${{ secrets.FLYWAY_TOKEN }}' }
      - name: Drift check only
        id: drift
        uses: red-gate/flyway-actions/migrations/checks@v2
        with:
          target-environment: production
          skip-code-review: 'true'
          skip-deployment-changes-report: 'true'
          skip-deployment-script-review: 'true'
          fail-on-drift: 'false'
          extra-args: -configFiles=ci/production.toml
      - name: Open or update a drift issue, then fail
        if: steps.drift.outputs.drift-detected == 'true'
        shell: bash
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh label create flyway-drift --force > /dev/null
          n=$(gh issue list --label flyway-drift --state open --json number --jq '.[0].number // empty')
          body="Drift detected in production. Run: $GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
          if [ -n "$n" ]; then gh issue comment "$n" --body "$body"
          else gh issue create --title "Flyway drift detected in production" --label flyway-drift --body "$body"; fi
          exit 1
```

With the change report skipped the action uses no build database. `gh` must be installed on a self-hosted runner. Drift resolution scripts upload as an artifact; triage is in file 14. For more targets, use a matrix with unique report names, or copy the job, each with its own read-only environment and `ci/` file. Drift is detectable only after a deployment has saved a snapshot.

## 14. Reusable workflows for many teams

File 11, section 14 describes one pipeline contract that every team's project calls. In GitHub that's a central repository of reusable workflows (`on: workflow_call`). Teams vary what happens before the pull request; the called workflows don't vary.

> Not from Redgate docs — starting point, validate in your environment.

```yaml
# Central repository: .github/workflows/flyway-deploy.yml
name: flyway-deploy
on:
  workflow_call:
    inputs:
      project-path:   { type: string, required: true }
      environment:    { type: string, required: true }   # test, uat or production
      runner-label:   { type: string, required: true }
jobs:
  deploy:
    runs-on: [self-hosted, windows, '${{ inputs.runner-label }}']
    environment: ${{ inputs.environment }}
    concurrency: { group: 'flyway-${{ inputs.project-path }}-${{ inputs.environment }}', cancel-in-progress: false }
    steps:
      - if: runner.os == 'Windows'
        shell: pwsh
        run: '"C:\Program Files\Git\bin", "C:\Program Files\Git\usr\bin" | Add-Content $env:GITHUB_PATH'
      # then the deploy-test steps from section 12, with working-directory: ${{ inputs.project-path }}
      # on each Redgate action and each run step after the download
```

> Not from Redgate docs — starting point, validate in your environment.

```yaml
# A team's repository
jobs:
  deploy-test:
    uses: <org>/<central-repo>/.github/workflows/flyway-deploy.yml@<tag-or-sha>
    with: { project-path: db/<project>, environment: test, runner-label: <runner-label> }

```

- Pin callers to a tag or commit SHA, and change the contract by pull request in the central repository with platform and DBA reviewers.
- Environment secrets can't pass through `workflow_call`; a called job that names an `environment` reads that environment's secrets and protection rules from the calling repository.
- A private central repository must allow access from the organization's repositories in its Actions settings.
- Ship the pull request, release and drift workflows the same way.

## 15. In daily use

- **Developers:** open a pull request; `validate` runs. A merge deploys to `test`, then `uat`.
- **Release managers:** start the release workflow with a green run's ID, read the production summary and report, then ask an approver.
- **DBAs:** watch for drift issues and approvals waiting stale.
- **Platform owners:** release new versions of the central workflows and track which teams have moved to them.

## 16. Limits

- Fork pull requests get no secrets, so only same-repository pull requests are validated.
- Private-repository approval gates and Enterprise Server artifact handling depend on your GitHub plan (section 6).
- `${env.X}` inside a `-configFiles` TOML, whether `-configFiles` adds to `flyway.toml`, the token variable's letter case, and the Key Vault resolver with your runner's identity are for your proof of concept to prove.
- Artifacts expire; promote within the retention period. The Docker build database is preview.
- `check -dryrun` shows SQL only; Java migrations and script callbacks appear by name.

## 17. Instructions for the AI assistant using this file

- Check the repository, the decision log (file 01) and file 10 for environments, runner labels, GitHub plan and authentication before writing a workflow. If the plan is unknown, ask before promising an approval gate.
- Use only the actions and inputs in section 3, all `flyway-actions` steps on one version. Never put a license key, password or token in YAML.
- Map exactly the `${env.X}` variables the loaded `ci/<env>.toml` needs: check account for checks, deploy account for deploys.
- Add the Git Bash step as the first step of every job on a Windows runner.
- Mark every workflow you write as composed and needing a proof of concept. Keep real deployment disabled until `testConnection`, `info` and `check -dryrun` work from the runner.
- Production deploys only after approval, from a verified tested run, one at a time. Never write a workflow that deploys to production on merge, or one that lets an AI tool deploy.
- Set `baseline-on-migrate: 'false'` for baselined databases. Never automate `repair`. Run `clean` only on `build`, shadow or scratch databases.
- On Enterprise Server, don't rely on `flyway-actions` artifact uploads or cross-run downloads; use section 6.
- For a CI tool other than GitHub Actions, apply file 11's design and say the syntax is outside this file.
- Answer in the language the person writes in. Keep commands, keys, file names and error text in English.
