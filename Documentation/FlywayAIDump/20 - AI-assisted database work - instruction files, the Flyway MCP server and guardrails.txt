## 1. The principle: the assistant proposes, Flyway produces what runs

The question isn't "do we use AI?" It's "who approves what AI writes to the database?" An assistant works against your own development database and the schema model. Flyway's comparison engine generates the migration that will run. That migration goes through the same gates as anyone's: code review (file 13), the pull request check, human reviewers and the pipeline's approvals (files 11 and 12). You don't have to trust the model; you have to trust your gates.

Nothing in this library has an assistant deploying to a shared environment. AI drafts, a person reviews, the pipeline deploys.

## 3. A sample instructions file

Save as `AGENTS.md` at the repository root and copy it where section 2 says. The assistant can fill each `{placeholder}` from what it works out about your project (file 01); delete the option that doesn't apply.

> Not from Redgate docs — starting point, validate in your environment.

```markdown
# Database changes in this repository

Every database change here goes through Flyway. These are rules, not preferences. If a task seems to need you to break one, stop and ask.

## Project facts
- Flyway project: {path to flyway.toml}. TOML only, never flyway.conf.
- Approach: [schema model plus generated migrations] [versioned migrations only].
- Environments you may use: development {dev env} (the engineer's own database), shadow {shadow env} (throwaway), build {build env} (the pull request check database). You have no others.
- Target platforms: SQL Server, Azure SQL Database and Azure SQL Managed Instance. Check the platform before you suggest syntax.
- Flyway is installed and licensed. Never run flyway auth and never ask for a token.
- Reference: the Flyway Library ({library path}). Start with file 00 and cite file numbers.
- Reply in the language the person writes in. Keep commands, keys, file names and error text in English.

## Rules
1. Route every schema change through Flyway. Change the development database, capture into the schema model, and generate one versioned migration and its undo. Never hand-edit an applied migration, and never hand-edit schema model files unless this team chose schema-model-first editing (file 08).
2. Never run DDL or DML against any database except development and shadow, by any route.
3. Never edit or rename a migration that is merged to main. Fix forward. Never run repair, clean, baseline or undo.
4. Put the ticket key {ticket key pattern} in the branch name, the migration description and the pull request title (file 30).
5. Never request, read, display or store production data or personal data.
6. Never ask for, accept or write credentials or connection strings. If you find one, stop and tell a human.
7. Before handing over, run flyway check -code -check.code.failOnError=true -environment={build env} and fix findings rather than weakening a rule.
8. Stop at a pull request for human review. Never merge, approve or deploy.
9. The Flyway MCP server is preview. Follow this workflow, not remembered tool names, and say so if a tool is missing.
10. Don't invent Flyway syntax. If a command fails, check https://documentation.red-gate.com/flyway and say what differed.
```

Keep it short; detail belongs in the library and in skills (file 21). On small-context models keep rules 1 to 3, 6, 8 and 10.

## 4. A path-specific file for migrations

Save as `.github/instructions/migrations.instructions.md`. Copilot chat in VS Code, Visual Studio and JetBrains, and Copilot code review on GitHub.com, apply it to matching files. For Kiro, the same text works as a `fileMatch` steering file; for Claude Code, as a `.claude/rules/` file with `paths:`.

> Not from Redgate docs — starting point, validate in your environment.

```markdown
---
applyTo: "**/migrations/**"
---
# Migration files
- A versioned migration is immutable once merged. Never edit one; add a new version.
- Flag: dropped tables or columns, narrowed column types, renames done as drop and create, a new NOT NULL column without a default, index builds on large tables.
- Check the version is higher than the highest on main, that a matching undo script exists, and that the ticket key is in the description.
- Do not suggest running the migration by hand against a shared database.
```

## 5. The Flyway MCP server (preview)

PREVIEW. Redgate's documentation says: "This feature is in preview and under active development. Tool names, parameters, and behavior may change significantly, or tools may be removed, in future releases without notice." Instruct agents by workflow, not by tool name, and read the release notes before you upgrade (file 25).

The server exposes the development workflow you'd run in Flyway Desktop or the CLI as tools an AI agent can call. It needs engine 13.0.0 or later and Flyway Enterprise. It's a local stdio server: your AI tool starts it as a process on your machine, so only tools that can launch a local process can use it. It calls no Redgate AI service; what the agent reads goes to your AI tool's own model, which is why file 03 matters.

Its boundary is your configuration: it applies changes to whatever the `[flywayDesktop]` development and shadow settings in `flyway.toml` point at. Redgate's page says that if those point elsewhere, or your AI tool edits `flyway.toml` directly, the boundaries don't apply.

Redgate's tool reference lists project tools (`load_project` first), schema model and development database diff and update tools, and, with `develop_migrations` only, checkpoint, `generate_migrations`, `review_code` and `test_migrate`.

- `generate_migrations` writes scripts from the schema model against the shadow database. From engine 13.10.0 an optional `generateUndoScripts` parameter overrides the project setting for one call.
- `review_code` reviews one script; it doesn't replace `flyway check -code` in the pull request check.
- `test_migrate` runs pending migrations against the shadow and stops at the first failure. Green proves a script runs, not that it's safe on production volumes.
- The three-sided diff (from engine 13.7.0) is for after you pull teammates' changes: take a checkpoint, pull, then diff. Changes are tagged `new`, `existing`, `missing` or `conflict`, so local work isn't overwritten.

It can't run `migrate`, `info`, `repair` or drift checks, and can't edit `flyway.toml`. Review each change with `get_diff_details` before an agent applies anything.

Documentation: https://documentation.red-gate.com/flyway/reference/usage/flyway-mcp-server/tool-reference

## 6. Prerequisites and starting the server

- Engine 13.0.0 or later, licensed and signed in for Flyway Enterprise (file 04). `flyway version` reports both.
- `flyway.toml` names a development and a shadow environment under `[flywayDesktop]`, matching environments defined in the file. Without them the toolsets fail with `error: No such environment`. A freshly created project often has neither filled in, so check before registering.
- Development is the engineer's own database; shadow is a throwaway database they own (file 16). Never point either at test, UAT or production.
- `-mcp.toolsets` has no default and is required; without it the server fails to start. Values: `develop_state` (schema model and development database kept in sync, no generation), `develop_migrations` (adds checkpoints, generation, test and review) and `all` (today identical to `develop_migrations`; Redgate advises a named toolset because `all` may change). `-mcp.maxLogs` defaults to 100.

The minimal command is `flyway mcp -mcp.toolsets=develop_state`. You don't run it yourself: your AI tool starts it from the `command` and `args` you register. Check `flyway version` works in a terminal first.

Both snippets below appear on Redgate's Flyway MCP Server page.

```toml
[flywayDesktop]
developmentEnvironment = "development"
shadowEnvironment = "shadow"

[flyway.generate]
types = ["versioned", "undo"]
```

Documentation: https://documentation.red-gate.com/flyway/reference/usage/flyway-mcp-server/mcp-server-configuration

## 7. Registering the server: the two Redgate-documented setups

Redgate's "Register with your AI tools" page documents two clients: Claude Code and VS Code with GitHub Copilot Chat. The `command` and `args` are the same; only the file and root key differ. Redgate's examples use a `<path to flyway>` placeholder, with `develop_state` on the registration page and `develop_migrations` on the configuration page; the blocks below follow its advice to use bare `flyway` from `PATH` in a committed file, and start with `develop_state`.

Claude Code, `.mcp.json` at the repository root, root key `mcpServers`:

> Not from Redgate docs — starting point, validate in your environment.

```json
{
  "mcpServers": {
    "flyway": {
      "type": "stdio",
      "command": "flyway",
      "args": ["mcp", "-mcp.toolsets=develop_state", "-mcp.maxLogs=100"]
    }
  }
}
```

VS Code, `.vscode/mcp.json`, root key `servers`:

> Not from Redgate docs — starting point, validate in your environment.

```json
{
  "servers": {
    "flyway": {
      "type": "stdio",
      "command": "flyway",
      "args": ["mcp", "-mcp.toolsets=develop_state", "-mcp.maxLogs=100"]
    }
  }
}
```

JSON can't carry the marker line, so say in the pull request that adds either file that it is a starting point. Points to know:

- VS Code also reads a portable `.mcp.json` (key `mcpServers`) at the workspace root, which Copilot harness sessions read directly. VS Code's page says servers in `.vscode/mcp.json` that need interactive inputs aren't forwarded to those sessions.
- If a GUI-launched tool on Windows can't find `flyway`, Redgate suggests `flyway.cmd`. Name the file exactly, with the leading dot, and restart the tool after editing.
- Every session starts with `load_project`, which needs the absolute path of the folder holding `flyway.toml` (Flyway Desktop may have used a subfolder). One registration per repository is enough; name each project's folder in the instructions file.
- Committing the file is a decision: Redgate warns that cloud-hosted agents that honor it may start the server for you. Record it in the decision log (file 01). Never put a token, password or connection string in any MCP file.
- Move to `develop_migrations` by pull request once the developer workflow in file 08 is routine.

Documentation: https://documentation.red-gate.com/flyway/reference/usage/flyway-mcp-server/register-with-your-ai-tools

```json
{
  "mcpServers": {

      "command": "flyway",
```

Organization controls:

- The "MCP servers in Copilot" policy is off by default for Copilot Business and Enterprise. It also governs agent mode and MCP in SSMS. An administrator turns it on before anyone sees the Flyway tools.
- An enterprise allow list can match a server by its command array. GitHub's page says the array must match the configured command exactly, so changing the toolset can take a developer outside the list.

## 9. Environments the assistant may touch

| Environment | Assistant may | Notes |
|---|---|---|
| `development` | Read, diff, apply selected changes | The engineer's own database |
| `shadow` | Build and test migrations | Throwaway; Test Migrate may reprovision it |
| `build` | Run `check` as an automated step | The pull request check database, owned by the pipeline |
| `test`, `uat`, `production` | Nothing | No credentials, no tools, no exceptions. The pipeline deploys here, behind approvals |

The same applies to assistants that act through your own database connection. Copilot in SSMS runs queries with your login's permissions and its agent mode can change schema with your approval, so open it only in a query window connected to your development database.

## 10. Human-in-the-loop guardrails

Your organization's AI policy governs; these rules sit inside it.

| Guardrail | In practice |
|---|---|
| AI drafts, a person reviews | Every generated or drafted migration goes through a pull request with code owners, `check -code` and the check build (files 08 and 13) |
| The pipeline deploys | No agent holds credentials for shared environments or runs `migrate`, `undo`, `repair`, `clean` or `baseline` against them (file 11) |
| No autonomous deployment | An assistant never deploys on its own, whatever tool or model it runs on (file 24) |
| No auto-approve | Leave tool approval on (Kiro `autoApprove`, Amazon Q "Always allow", SSMS and Visual Studio tool toggles) for anything that changes a database |
| No production or personal data | Development and shadow hold schema, empty tables or synthetic rows only |
| No credentials in prompts or files | Flyway resolves secrets at run time (file 10) |
| Approved tools only | Use only tools and models your organization approved (file 03). Flyway Desktop AI services (preview) and SQL Prompt AI are governed by one organization-wide switch in the Redgate portal; the MCP server sits outside it |
| Agents that route around Flyway | Redgate's own published experiments show coding agents reaching for an application ORM's migration tool, or a general-purpose database MCP server with a run-any-SQL tool, even when told to use Flyway. Neither leaves a migration, a check or a history row. Register only the Flyway MCP server against development and shadow, leave other database tools unregistered or read-only, and don't use community Flyway MCP servers that run `repair` or `migrate` from chat: an agent that can run `repair` can erase the checksum evidence that an applied script was edited |
| AI-written pipeline files | Review network rules, secrets and environment separation by hand. A Redgate-published walkthrough had an assistant scaffold a working pipeline quickly and also propose insecure network choices a person had to reject (files 11 and 12) |
| Evidence from your trail | Redgate doesn't document the MCP server's local logs as an audit record. Use Git, the pull request, pipeline logs and the schema history table (file 17) |

Prompts aren't the control. The pull request, code review, the build and drift checks (file 14) are. A change made outside Flyway shows up as drift.

## 11. Prompts that work, and what to keep out

| Job | Prompt | Load |
|---|---|---|
| Migration from a ticket | "Ticket `<ticket-key>`: add column `<column>` to `<table>`. Follow file 08. Show the schema model diff first and apply nothing. Then generate the migration and undo, list risky changes, and stop at a pull request." | Files 08 and 30 |
| Review a pull request | "Review this migration and its undo with the review card in file 27. Say what you can't tell from the diff." | Files 13 and 27 and the diff |
| Explain a check report | "Which findings in this check report block the merge, which are noise, and what is the smallest fix? Names removed." | Files 13 and 22 and the report |

Add "name the file and section you used" to any of them.

Keep out of every prompt: production data and query results from shared databases, personal data, connection strings, passwords and tokens, and server, database and client names unless your policy allows them. If you paste one by mistake, stop, tell your security contact, and rotate any credential.

## 13. Limits

- The Flyway MCP server is preview, works on development and shadow only, and has no migrate, info, deploy or drift tool. Use the CLI and the pipeline (files 11 and 12).
- Redgate documents registration for Claude Code and VS Code only. Every other setup in section 8 is the vendor's format, untested by Redgate.
- Redgate's MCP pages don't list supported databases. Prove your SQL Server and Azure SQL setup on a development database first.

## 14. Instructions for the AI assistant using this file

- Label the Flyway MCP server, Flyway Desktop AI services and Redgate Assistant as preview whenever you mention them.
- When describing MCP setup, say whether it is Redgate-documented (section 7) or vendor-documented (section 8).
- Never request, display or store production data or credentials. If a user pastes either, stop, say so and don't repeat it.
- Point the MCP server and any Flyway command you run only at development and shadow. Refuse anything that changes test, UAT or production; hand it to the pipeline (file 11).
- Before MCP setup, ask which AI tools the team uses, check `flyway.toml` has development and shadow environments, and ask whether the team commits the MCP file.
- Start every MCP session by loading the project, then show changes before applying any. Stop at a pull request.
- For skills, file 21. For loading the library, file 03. For a failure, file 22.
- Answer in the language the person writes in. Keep commands, keys, file names and error text in English.
