## 1. How configuration is layered

| Layer | Where | Use for |
|---|---|---|
| `flyway.toml` | Project root, committed | Shared settings, development and shadow environments, comparison settings |
| `flyway.user.toml` | Project root, git-ignored | One developer's own connection details |
| `ci/<environment>.toml` | Committed, loaded with `-configFiles` | One deployed environment each |
| Environment variables | Runner, job step, shell | Secrets and per-run values |
| Command-line parameters | The command | One-off overrides |

Redgate's precedence page lists command-line arguments first, then environment variables, standard input, configuration files and defaults. `-configFiles` loads files in addition to those loaded automatically, with relative paths resolved against the working directory. Don't prefix `-configFiles` or `workingDirectory` paths with `filesystem:`; that prefix belongs on `locations` only.

If Flyway finds a TOML file it ignores `.conf` files, so a stray `flyway.toml` can silently disable an older `flyway.conf` project. When a value isn't what you expect, run the command with `-X` (debug output).

Documentation: https://documentation.red-gate.com/fd/configuration-precedence-277578840.html

## 2. Anatomy of flyway.toml

| Section | Holds | Who edits it |
|---|---|---|
| Root keys `id`, `name`, `databaseType` | Project identity | Written by Desktop or `flyway init`; leave alone |
| `[environments.<name>]` | `url`, `user`, `password`, `schemas`, `provisioner`, `jdbcProperties`, and resolvers under `[environments.<name>.resolvers.<resolver>]` | DBAs |
| `[flyway]` and namespaces such as `[flyway.generate]`, `[flyway.placeholders]` | Locations, validation, history table, generation | DBAs, by pull request |
| `[flywayDesktop]` | Which environments Desktop uses as development and shadow | Written by Desktop |
| `[redgateCompare.sqlserver]`, `[[redgateCompare.staticDataTables]]` | `filterFile`, comparison `options.behavior` and `options.ignores`; static data tables | DBAs, by pull request |

The `[flywayDesktop]` keys are `developmentEnvironment` and `shadowEnvironment`. That's what `flyway init` writes, and what Redgate's Flyway MCP server page (preview) and Enable migrations tutorial show. The Desktop namespace reference pages list `development` and `shadow` instead; don't copy those. If a working file already has keys, leave them. If Desktop asks for connection details on opening the project, a key's value doesn't match an environment name.

`flyway init` and Desktop write `outOfOrder = true` and `mixed = true` even though the engine defaults are `false`. Read your own file (file 09 covers `outOfOrder`). Add `flyway.user.toml` to `.gitignore`; a pipeline credential never lives there.

Documentation: https://documentation.red-gate.com/flyway/reference/configuration/flyway-desktop-namespace

## 3. Recognizing a fresh project vs a configured one

A `flyway.toml` existing doesn't mean a team has set Flyway up. `flyway init` and Desktop's new-project flow write a complete-looking file in seconds. Redgate's Init command page says only that `init` "generates a new Flyway project, complete with recommended files and configuration for a given database type". Redgate's own command-line workbook shows what that means for SQL Server:

- Root keys `databaseType`, `name` and a generated `id`.
- `[flyway]` with `locations = [ "filesystem:migrations" ]`, `mixed = true`, `outOfOrder = true` and `schemaModelLocation = "schema-model"`. Other non-default values, such as `validateMigrationNaming`, depend on the version that created the project, so read the file rather than a list.
- `[flywayDesktop]` with `developmentEnvironment = "development"` and `shadowEnvironment = "shadow"`.
- An empty `migrations/` folder, an empty `schema-model/` folder, a default `Filter.scpf` and a `.gitignore`.
- No `[environments.*]` tables. The workbook says "By default, no database connections are configured".

Desktop adds development and shadow connections when someone links a database, by default in the git-ignored `flyway.user.toml`, so a committed file can look empty even on a developer's working copy.

Redgate also publishes sample projects (the Autopilot templates) whose `flyway.toml` defines `development`, `shadow`, `Build`, `Check`, `Test` and `Prod`, all pointing at `localhost` sample databases with `integratedSecurity=true`, `trustServerCertificate=true` and `baselineOnMigrate = true`, plus example migrations. A file shaped like that is a copied template, not a configured estate.

| Signal | Fresh or template | Configured and in use |
|---|---|---|
| `[environments.*]` | None, only `development` and `shadow`, or `localhost` sample names | Real targets through placeholders and `${env.X}`, or `ci/<environment>.toml` files |
| `migrations/` | Empty, or only sample scripts | A baseline (`B`) script or a chain of versioned scripts with team ticket keys |
| `schema-model/` | Empty | Object folders matching your database |
| `Filter.scpf` | Unchanged default | Edited, committed, reviewed |
| Settings | `mixed`, `outOfOrder` and `baselineOnMigrate` exactly as generated | Values someone changed deliberately, with a reason in the pull request or decision log |
| Pipeline | No `.github/workflows/` using Flyway, no `ci/` folder | Workflows that load the `ci/` files |
| Git history | One "initial" commit | Commits from several people over time |
| Targets | `flyway info` shows no schema history table | `flyway info` shows applied migrations |

What the assistant does with this:

- Treat a fresh or template project as a starting point. Don't describe environments, baselines, approvals or pipelines as existing because the file mentions them.
- Before advising on a generated setting, say it was written by the generator, not chosen: `outOfOrder = true` and `mixed = true` are the usual examples (file 09, and section 11 of this file).
- Ask before assuming a `localhost` URL, a sample database name or `trustServerCertificate=true` is intentional.
- For a configured project, read its settings as decisions and change them only by pull request.

## 4. JDBC URLs: on-premises SQL Server and Azure SQL

On-premises forms (`<server>`, `<db-name>`):

| Case | URL |
|---|---|
| Default instance | `jdbc:sqlserver://<server>:1433;databaseName=<db-name>;encrypt=true` |
| Named instance | `jdbc:sqlserver://<server>;instanceName=<instance>;databaseName=<db-name>;encrypt=true` |
| Named instance, fixed port | `jdbc:sqlserver://<server>:<port>;databaseName=<db-name>;encrypt=true` |
| Windows authentication | add `integratedSecurity=true` and omit `user` and `password` |

- A named instance without a port relies on the SQL Server Browser service. Where it's blocked, use the fixed port (with both, the driver uses the port).
- Set `encrypt=true`, use a certificate the runner trusts, and leave `trustServerCertificate` unset. `true` skips validation, so limit it to private development networks and record it in your decision log (file 01).
- `integratedSecurity=true` on Windows needs the driver's `mssql-jdbc_auth` DLL. The Windows command-line package carries it in its `native` folder, and Redgate's Windows authentication tutorial needs no extra steps. Linux runners use Kerberos (`authenticationScheme=JavaKerberos`, Redgate's Kerberos tutorial).

Azure SQL. This library covers both Azure SQL Database and Azure SQL Managed Instance, and an estate can hold both. The same driver settings and Entra options apply to each; the host differs, so the host name tells you which one a URL points at. A Managed Instance's VNet-local endpoint is reached from inside the network, which usually means a self-hosted runner (file 12):

| Service | Host and port |
|---|---|
| Azure SQL Database | `<azure-sql-server>.database.windows.net`, port 1433 |
| Managed Instance, VNet-local endpoint | `<mi-name>.<dns-zone>.database.windows.net`, port 1433 |
| Managed Instance, public endpoint (if enabled) | `<mi-name>.public.<dns-zone>.database.windows.net`, port 3342 |

> Not from Redgate docs — starting point, validate in your environment.

```text
jdbc:sqlserver://<azure-sql-server>.database.windows.net:1433;databaseName=<db-name>;encrypt=true
```

Add `authentication=<value>` to choose how the driver signs in with Microsoft Entra. Floors are Microsoft JDBC driver versions, from Microsoft Learn:

| Value | Use | Driver floor and notes |
|---|---|---|
| `ActiveDirectoryServicePrincipal` | Pipeline service principal (in Redgate's Entra tutorial) | 9.2. `user` is `<client-id>`, `password` the secret |
| `ActiveDirectoryServicePrincipalCertificate` | Service principal with a certificate | 12.4 |
| `ActiveDirectoryMSI` | Self-hosted runner on Azure with a managed identity (in Redgate's tutorial) | 7.2. `msiClientId=<client-id>` for a user-assigned identity. Newer name `ActiveDirectoryManagedIdentity`, 12.2 |
| `ActiveDirectoryDefault` | Whatever the Azure credential chain finds (environment variables, managed identity, Azure CLI sign-in) | 12.2. A Microsoft driver mode Redgate's tutorials don't cover: prove it in your POC before a pipeline depends on it |
| `ActiveDirectoryInteractive` | Developer browser sign-in | 9.2. Prompts on every call without the resolver below |
| `ActiveDirectoryIntegrated` | Domain-joined machine federated with Entra | 6.0. Auth DLL or Kerberos |
| `ActiveDirectoryPassword` | Entra user and password | Deprecated by Microsoft; fails where MFA is enforced |

The command line ships the Microsoft driver plus Microsoft's `azure-identity` and `msal4j` libraries, so no extra jars are needed for these modes. Redgate's engine release notes record the driver upgrade to `mssql-jdbc` 12.10.2 in engine 11.16.0, which clears every floor in the table; file 25 records what was checked. Confirm on your own install by looking at the `mssql-jdbc-<version>.jar` in the `drivers` folder, then run `flyway testConnection -environment=<env>`, which tests Flyway's and the comparison engine's connections.

Redgate documents four Entra routes for SQL Server: service principal, managed identity (`ActiveDirectoryMSI`), interactive sign-in through the Entra resolver, and an access token fetched with `az account get-access-token`. Start with one of those.

For developer machines, the Microsoft Entra Interactive resolver caches the token. It needs `tenantId` and `clientId`:

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.development]
url = "jdbc:sqlserver://<azure-sql-server>.database.windows.net:1433;databaseName=<db-name>;encrypt=true"

[environments.development.jdbcProperties]
accessToken = "${entraId.token}"

[environments.development.resolvers.entraId]
tenantId = "<tenant-id>"
clientId = "<client-id>"
```

For pipelines, Redgate's Entra tutorial also documents an access token in `jdbcProperties.accessToken` (section 7): https://documentation.red-gate.com/fd/tutorial-connect-using-microsoft-entra-id-339477241.html

## 5. The six environments

| Environment | What it is | Defined in | Provisioner | Connects as |
|---|---|---|---|---|
| `development` | A developer's own database (file 08) | `flyway.toml`, no credentials | None | Developer role |
| `shadow` | Flyway's throwaway comparison database | `flyway.toml` | `clean` | Developer role |
| `build` | CI throwaway for proving migrations and the schema model | `ci/build.toml` | `clean` | Deploy account on a build server |
| `test` | Shared test database | `ci/test.toml` | None, ever | Deploy account to deploy; read-only check account for `info` |
| `uat` | Pre-production | `ci/uat.toml` | None, ever | Same |
| `production` | Production | `ci/production.toml` | None, ever | Same, behind approval |

The admin role creates databases, logins and the accounts above. It isn't used by Flyway in any pipeline.

- On SQL Server the shadow is a separate database, not a schema. Each developer who generates migrations needs their own, on a non-production server.
- The `clean` provisioner re-provisions an existing database by cleaning it; it can't create one. The other provisioners are (preview), and file 16 covers them and Azure SQL.
- Never give a long-lived database a provisioner. Provisioning runs before any command connects.
- If build or shadow databases hold objects in several schemas, check what `clean` drops. On SQL Server, `[flyway.sqlserver.clean] mode` controls it (Redgate's SQL Server Clean Namespace page).
- Never set `[flyway] environment` to a deployed environment. Workflows pass `-environment=` every time.

Documentation: https://documentation.red-gate.com/flyway/flyway-concepts/environments/shadow-and-build-environments

## 6. One ci file per environment

Flyway resolves every `${env.X}` in every file a command loads, including environments the command doesn't use. One file that references every environment's secrets fails in every step, because a `test` step only has test's secrets. Keep one small file per environment and have each step load only its own.

> Not from Redgate docs — starting point, validate in your environment.

```toml
# ci/uat.toml - loaded only by steps that touch uat
[environments.uat]
url = "${env.FLYWAY_UAT_URL}"
user = "${env.FLYWAY_UAT_USER}"
password = "${env.FLYWAY_UAT_PASSWORD}"
```

> Not from Redgate docs — starting point, validate in your environment.

```bash
flyway info -configFiles=ci/uat.toml -environment=uat
```

- Give each environment its own variable names, so a test secret mapped into a production step fails to resolve instead of connecting. A read-only check step and a deploy step map different secrets into the same names, so one file serves both.
- Prove `${env.X}` inside a `-configFiles` TOML in the proof of concept (file 05): run `flyway info -X` with the file and check the URL and user resolved.
- The fallback needs no resolver. Redgate's Environments Namespace page documents setting any environment setting from a variable named `environments_<environment>_<setting>`, for example `environments_uat_password`, with one more underscore per nested level (`environments_uat_jdbcProperties_accessToken`). The `environments_` prefix is case-insensitive, but `jdbcProperties` keys pass to the driver verbatim, so keep their casing. Use letters, digits and underscores in environment names.
- `FLYWAY_URL`, `FLYWAY_USER` and `FLYWAY_PASSWORD` are the legacy root settings. Flyway maps them to an environment named `default`, so they don't configure `uat`.

Documentation: https://documentation.red-gate.com/fd/environments-namespace-277578909.html

## 7. Secrets: environment variables, GitHub secrets and resolvers

No password, token, permit or credential-bearing URL goes in a committed file, a workflow log or an AI chat.

In order of preference:

1. No stored secret: a managed identity on a self-hosted runner, OIDC to Azure for an access token, or OIDC followed by the Azure Key Vault resolver (below). On-premises, Windows integrated authentication or Kerberos under the runner's service account (file 12).
2. GitHub environment secrets, one environment per target (`test`, `uat`, `production`). They reach only jobs that name the environment, and for `production` only after required reviewers approve.
3. Repository secrets for values every job needs, such as `FLYWAY_EMAIL` and `FLYWAY_TOKEN` for a service account. Air-gapped runners use `FLYWAY_OFFLINE_PERMIT_PATH`. Never write a license key.

A step maps secrets into its environment, and the `ci/` file reads them:

> Not from Redgate docs — starting point, validate in your environment.

```yaml
      - name: Deploy to uat
        env:
          FLYWAY_EMAIL: ${{ secrets.FLYWAY_EMAIL }}
          FLYWAY_TOKEN: ${{ secrets.FLYWAY_TOKEN }}
          FLYWAY_UAT_URL: ${{ secrets.FLYWAY_UAT_URL }}
          FLYWAY_UAT_USER: ${{ secrets.FLYWAY_UAT_USER }}
          FLYWAY_UAT_PASSWORD: ${{ secrets.FLYWAY_UAT_PASSWORD }}
        run: flyway migrate -configFiles=ci/uat.toml -environment=uat
```

The job carries `environment: uat` (file 12 has the whole shape). Fork pull requests receive no secrets.

For Azure SQL without a stored database secret, sign in with `azure/login` using OIDC, fetch a token and map it to the access token property:

> Not from Redgate docs — starting point, validate in your environment.

```yaml
      - uses: azure/login@v3
        with:
          client-id: <client-id>
          tenant-id: <tenant-id>
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Get SQL token
        shell: bash
        run: |
          TOKEN=$(az account get-access-token --resource https://database.windows.net/ --query accessToken -o tsv)
          echo "::add-mask::$TOKEN"
          echo "environments_uat_jdbcProperties_accessToken=$TOKEN" >> "$GITHUB_ENV"
```

The token command is from Redgate's Entra tutorial; the variable follows the documented form (section 6). Keep `shell: bash` on Windows runners, whose default shell is PowerShell. On this path the `ci/` file carries no `user` or `password`, because every `${env.X}` it names must resolve. The identity needs a database user (`CREATE USER [<app-name>] FROM EXTERNAL PROVIDER`) with the deploy role.

Resolvers fetch values at run time, using `${resolver.key}` and configured under `[environments.<name>.resolvers.<resolver>]`. Use only resolvers on Redgate's Environment Resolvers Namespace page. Relevant here: Environment Variable (`${env.X}`), Azure Key Vault, Microsoft Entra Interactive, Git, Local Secret and Vault.

On developer machines, `flyway.user.toml` keeps connection details out of Git, but it isn't encrypted. Only operating-system file permissions protect it, and a script callback running as that user can read it. Describe it to your security team as "not committed", never as secure storage. Prefer Windows authentication or Entra for development connections, and where a password can't be avoided, use the Local Secret resolver instead of writing the password into the file.

The Azure Key Vault resolver (Flyway Enterprise, from engine 12.5.0) takes one setting, `vaultUrl`. Desktop honors it but can't set it. Redgate prefers this per-environment resolver to the older global `[flyway.akv]` settings:

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.uat.resolvers.azureKeyVault]
vaultUrl = "https://<vault-name>.vault.azure.net"

[environments.uat]
password = "${azureKeyVault.<secret-name>}"
```

What's documented and what to prove:

- How the resolver signs in to Key Vault: Flyway relies on the Azure SDK's standard credential chain, the same one other Azure tools use, through the `azure-identity` library the command line bundles. It takes whichever identity the runner has: a service principal through the `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_CLIENT_SECRET` environment variables, a workload identity, a managed identity on a self-hosted runner in Azure, or an Azure CLI sign-in. An `azure/login` step in GitHub Actions leaves an Azure CLI sign-in, and the resolver honors it, so `azure/login` with OIDC followed by the resolver needs no stored vault secret. Redgate's resolver page documents the settings, not this chain, so still read one test secret with your runner's exact identity in your proof of concept before a pipeline depends on it.
- Permission, from Microsoft's Key Vault docs: the **Key Vault Secrets User** role on vaults using Azure role-based access control, or the secret **Get** permission on vaults still using access policies. Grant it on the one vault, not the subscription; Microsoft recommends one vault per application per environment, with roles assigned at vault scope.
- Use the resolver for environment connection settings (`url`, `user`, `password`), which is where Redgate documents it. Don't rely on it inside `[flyway.placeholders]` without proving it.
- If the resolver doesn't fit your security model, the fallback is `azure/login` plus a step that reads the secret (`az keyvault secret show`) into a masked variable and passes it as `${env.X}`.

Always write environment variables as `${env.X}`. A few Redgate pages show `${FLYWAY_PASSWORD}` without `env.`; the Environment Variable resolver page documents the `env.` form.

Resolvers can't be nested. To stop a stray value injecting characters, add a filter: `${resolver.key:AD}` keeps letters and digits, `:ad` keeps ASCII letters and digits only. Escape a literal `${...}` as `$${...}`.

Never put a secret in `[flyway.placeholders]`. Placeholder values end up in the SQL that runs, and Redgate's pages show resolvers configured only inside environments.

Documentation: https://documentation.red-gate.com/fd/environment-resolvers-namespace-277578931.html

## 8. Placeholders

Placeholders replace `${key}` in versioned and repeatable migrations and SQL callbacks.

> Not from Redgate docs — starting point, validate in your environment.

```toml
[flyway.placeholders]
reportingRole = "<reporting-role>"
```

- Command line: `-placeholders.reportingRole=<value>`. Environment variable: `FLYWAY_PLACEHOLDERS_<KEY>`.
- Built-in: `${flyway:defaultSchema}`, `${flyway:user}`, `${flyway:database}`, `${flyway:environment}` and `${flyway:timestamp}`.
- Redgate's docs: changing a placeholder value re-applies repeatable migrations on the next `migrate`.
- Placeholders aren't documented for state-based deployment scripts (`prepare` and `deploy` from the schema model). Don't rely on them there.
- Use them for values that differ per environment, such as a linked server name.

## 9. Filters and SQL Server comparison options

The filter file removes objects Flyway doesn't own from capture, generation, `prepare`, change reports and drift checks. On SQL Server it's a SQL Compare filter, `Filter.scpf` (resolved relative to the working directory) by default, or the path in `[redgateCompare.sqlserver] filterFile`, which also takes `-redgateCompare.sqlserver.filterFile=` for one run. By default Flyway already filters out users and objects holding secure information, such as certificates. Don't use the generic `[redgateCompare] filterFile` for SQL Server; remove it from an older project. File 09 has a team-scoping filter example.

- Filters apply after comparison, so they don't speed it up, and a filtered object can still be pulled into a script as a dependency.
- On SQL Server the environment `schemas` setting is ignored by `diff` and `prepare`, and Desktop says not to set it. The filter is the scope.
- Edit in Desktop's filter editor, or SQL Compare's for complex rules, and commit the result. Filter objects another system manages, and scratch objects by naming convention.

Comparison options live under `[redgateCompare.sqlserver.options.behavior]` and `[redgateCompare.sqlserver.options.ignores]`. Settings in `ignores` are booleans named for what they ignore, such as `ignoreWhiteSpace`, `ignoreComments` and `ignorePermissions`.

> Not from Redgate docs — starting point, validate in your environment.

```toml
[redgateCompare.sqlserver.options.ignores]
ignoreWhiteSpace = true
```

Flyway fixes some options that SQL Compare lets you change: it always compares check constraints, keys, constraint names, identity properties and trigger order, and generates scripts without transactions or error handling. That explains most "SQL Compare shows a difference Flyway doesn't" questions (file 19). Each ignore hides real drift, so make each one a recorded decision. Redgate's `prepare` page says options and static data are read only from TOML, not the command line.

Documentation: https://documentation.red-gate.com/flyway/reference/configuration/redgate-compare-namespace/redgate-compare-sql-server-namespace

## 10. Per-environment overrides, and the 13.10.0 note

A `flyway` table inside an environment overrides root `[flyway]` settings for that environment only. An overridden key replaces the root value in full (a `locations` list isn't merged with the root list); keys you don't set keep their root value:

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.test.flyway]
locations = ["filesystem:migrations", "filesystem:migrations-test"]
```

Redgate's Environment Overrides page now says: from engine 13.10.0, parameters outside the flyway namespace, such as `check.buildEnvironment`, override the same way, and an unknown key is an error. Only `environment` itself can't be overridden (`email`, `token` and the license key can be, but shouldn't), nor can command-line-only parameters such as `configFiles`. The command-line form is `-environments.<env>.flyway.<setting>=<value>`; there's no environment variable form. Prove an override with `-X` on your pinned engine before a pipeline depends on it.

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.uat.flyway]
check.buildEnvironment = "build"
```

Keep per-run choices such as `cherryPick` and `target` on the command line, never in a `ci/` file.

The same sub-table turns Flyway Insights (preview) on for chosen environments only: `publishResult = false` under `[flyway]` and `publishResult = true` under `[environments.<name>.flyway]`, on an engine later than 13.10.0, proven on your version (file 18, section 7).

Documentation: https://documentation.red-gate.com/fd/environment-overrides-295176010.html

## 11. Safety settings worth writing down

| Setting | Value | Why |
|---|---|---|
| `cleanDisabled` | `true` | The default. Writing it makes the intent reviewable. Clean only build, shadow or scratch databases |
| `validateMigrationNaming` | `true` | Default `false`, which skips misnamed files |
| `failOnMissingLocations` | `true` | Default `false`; a mistyped location builds a smaller schema and reports success |
| `outOfOrder` | `false` on shared environments (the strict stance), or `true` everywhere only if the project chose the permissive stance with its two-order build | File 09, section 5 |
| `mixed` | `false` | `flyway init` writes `true` |
| `installedBy` | The workflow run ID, passed on the command | History rows trace to a run |
| `saveSnapshot` | `true` on deployed runs, on the command line | Default `false` on the CLI; drift checks need it (file 14) |

Repair is never automated: a person runs `repair` after reading `info`. Production runs from an on-demand workflow behind approval (file 11).

## 12. A complete example: flyway.toml and ci/uat.toml

> Not from Redgate docs — starting point, validate in your environment.

```toml
# flyway.toml - committed, no credentials
id = "<written by Desktop>"
name = "<service name>"
databaseType = "SqlServer"

[flywayDesktop]
developmentEnvironment = "development"
shadowEnvironment = "shadow"

[flyway]
locations = ["filesystem:migrations"]
validateMigrationNaming = true
failOnMissingLocations = true
cleanDisabled = true
outOfOrder = false
mixed = false

[flyway.generate]
types = ["versioned", "undo"]
timestamp = "always"

[redgateCompare.sqlserver]
filterFile = "Filter.scpf"

[environments.development]
url = "jdbc:sqlserver://<server>:1433;databaseName=<db-name>_dev;encrypt=true;integratedSecurity=true"

[environments.shadow]
url = "jdbc:sqlserver://<server>:1433;databaseName=<db-name>_shadow;encrypt=true;integratedSecurity=true"
provisioner = "clean"

[environments.build]
url = "jdbc:sqlserver://<server>:1433;databaseName=<db-name>_build;encrypt=true"
provisioner = "clean"
```

Add `ci/uat.toml` from section 6. The `build` environment carries no user and password in the committed file; the step that uses it supplies them through `ci/build.toml`.

## 13. In daily use

DBAs change configuration by pull request, with code-owner review on `flyway.toml`, `ci/`, filters and `.github/workflows/`. Show the effect in the pull request: `flyway info -X -configFiles=ci/<env>.toml -environment=<env>` against `test`, and a `flyway diff` if a filter changed. Nobody edits configuration on a runner. Record decisions in your decision log (file 01).

After a URL or credential change, run `flyway testConnection -environment=<env>`. It changes nothing and, unlike `info`, runs no callbacks or validation.

## 14. Limits

- The Azure Key Vault resolver signs in through the Azure SDK credential chain, which Redgate's resolver page doesn't spell out. Prove your runner's identity on a test secret before relying on it (section 7).
- `${env.X}` inside a `-configFiles` TOML is proven in the proof of concept, not assumed. The `environments_<env>_<setting>` variables are the documented fallback.
- The SQL Server driver page doesn't state the bundled driver version; the engine release notes do (section 4). Check the `drivers` folder after each upgrade.
- What can be overridden per environment depends on the engine (widened in 13.10.0). Prove it.
- How a second config file overrides a table array, such as `[[redgateCompare.staticDataTables]]`, isn't documented.

## 15. Instructions for the AI assistant using this file

- Never write a password, token, permit, license key, credential-bearing URL or real host name into any file. Use `${env.X}` and the placeholders `<server>`, `<db-name>`, `<azure-sql-server>.database.windows.net`, `<tenant-id>` and `<client-id>`.
- Before adding `${env.X}` to a file, ask which steps load it and confirm each can resolve it. Use one `ci/<environment>.toml` per environment.
- Work out whether each target is on-premises SQL Server, Azure SQL Database or Managed Instance from its host name (section 4) or the discovery in file 01. If neither tells you, ask; never assume one for the whole estate.
- Before describing a project, check the section 3 signals. Never treat a freshly generated or template `flyway.toml` as evidence that environments, baselines or pipelines exist.
- Use only resolvers on Redgate's resolvers page (section 7). Never invent a resolver or a setting.
- Never enable clean outside build, shadow or scratch, and never add a provisioner to a shared environment.
- For any 13.10.0 per-environment override, say it needs proving with `-X`.
- When a setting isn't taking effect, ask for the command and its `-X` output first.
- For `[flywayDesktop]`, write `developmentEnvironment` and `shadowEnvironment`. If a working file already has keys, leave them.
